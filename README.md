# pi-continuation

Experimental, private Pi extension for explicitly registered Herdr-managed Pi TUI sessions. **Not released or installed into live Pi settings.** The personal GitHub repository is public; npm publication is disabled (`private: true`). Linux, macOS and native Windows are targets, **not verified support claims**. The contract and tested limits are in [docs/contract.md](docs/contract.md).

## What it does

- A worker registers its **current saved Pi session** and an existing checkpoint; observation begins paused. A fork or replacement session cannot inherit this binding. Pi's native Herdr integration still owns session and status reporting.
- A dedicated supervisor claims a local exclusive owner, checks Herdr's session/terminal/workspace/pane identity and persistent worker stops, and can dispose of each stop through a model tool. Registration and activation at global, route, and worker levels are separate TUI-confirmed actions. Model tools cannot activate scopes.
- Continuation is delivered to a worker-owned local socket, not through `agent.prompt`. The worker checks its own native session, exact stop, idle state, active owner and all pauses before injecting a Pi custom message. An uncertain delivery pauses that worker; old receipts cannot be retried. Escape, tool errors, observed UI approval prompts, and raw keyboard input to a registered worker produce sticky holds requiring explicit human clearing.
- Two nudges without new checkpoint evidence pause only the affected worker and queue one blocker notice when a coordinator is bound. Unresolved supervisor turns get one corrective wake, then a worker-local pause. Material completion/blocker/decision notices can be queued for a registered exact coordinator session; busy or blocked recipients remain deferred and stale completion is discarded. A lost or replaced coordinator pauses only its route; a lost worker or checkpoint pauses only that worker. Blocker/decision notices dispose the stop and pause the worker before delivery. No coordinator receives approval authority.

The packed artifact was loaded by an isolated, in-memory Pi 1.5.0 SDK session on Linux. A refactored candidate was exercised in disposable Linux Pi/Herdr TUI sessions against a loopback scripted model: a final-reply decision reached an exact coordinator while the worker remained held. A separate disposable test confirmed that explicit first-turn registration yields a completed, unheld stop; isolated interleaving tests exercise cancellation when a prompt or turn starts during registration. A separate blind model review selected acceptable dispositions for 12/12 synthetic narrative stops; it did not exercise the native supervisor tool loop. These tests do not prove general model judgment or every live prompt ordering. Isolated CI tests and package checks passed on Ubuntu, macOS and Windows; credentialed Pi/Herdr runtime behavior on those platforms remains unverified. The worker now attaches its bounded final reply to the exact stop, and the supervisor reviews it alongside the checkpoint before disposition. A reply requesting approval can be cited for a decision notice or pause without rewriting the checkpoint. This preserves the current judgment-based workflow, not a hard guarantee: a model can still misread a prose-only request. Pi's UI-prompt notification is best-effort rather than awaited; the worker must load this extension first so its prompt hold cannot sit behind another handler. A synchronous shared-UI guard now catches fully overlapping shared-context dialogs. A native Pi 1.5.2 TUI probe verified that fix **and an uncovered alternate shortcut-context gap**; first-option loading does not fix that gap. Full prompt coverage and prose-approval safety are not established; real-worker activation remains blocked. See [the validation evidence and limits](docs/validation.md). Do not connect this package to existing workers or rely on it to replace existing supervision on the strength of this repository alone.

Selected-worker ownership handoff is now source-prepared: a shared per-worker witness fences cooperating owners, blocks rollback after attempted delivery or observed progress, and restores only the selected old worker paused. Its private legacy adapter has been exercised only in a disposable copy, not installed into active supervision. The package's JSON handoff attachment keeps scopes paused, skips the inherited stop and conservatively exhausts the initial budget. It does not import/redeliver old pending notices or establish live migration readiness. See [the handoff contract](docs/contract.md#selected-worker-ownership-handoff-source-preparation). Approval and runtime gates remain unresolved.

## Development / dry-run setup

Run `npm ci --legacy-peer-deps`, `npm test`, and `npm pack --dry-run`. Tests use fake Pi contexts, fake Herdr sockets, local loopback sockets, temporary files and competing child processes; they do not touch real workers. CI runs isolated tests and payload checks on Linux, macOS, and Windows; a passing check does not establish supervised runtime support. Pi 1.5.0 and Herdr 0.9.5 (protocol 22) are the current development baseline, not a verified cross-platform support matrix. The package has one explicitly listed extension entrypoint and an explicit npm file allowlist; tests, local plans and checkpoint files are excluded.

For a **separately authorized disposable** installation only, Pi accepts a local package with `pi install /absolute/path/to/pi-continuation` (this changes Pi settings). A disposable worker must start Pi with `-e /absolute/path/to/pi-continuation/src/extension.ts` as the **first Pi option**, before other flags or `-e` extensions. Pi loads explicit extensions ahead of discovered packages; registration and restore refuse a worker started without this ordering. An existing worker cannot gain this guarantee merely by installing the package into its running Pi process. Activation is **disabled by default** while the full approval contract and handoff remain unverified. Only a separately authorized disposable test can opt in by starting the test supervisor with `PI_CONTINUATION_EXPERIMENTAL_ACTIVATION=1`; this flag is not a safety fix or permission to bind real workers. The intended TUI command sequence for such a disposable test is:

1. In each disposable worker launched with this extension first, `/continuation-worker --start {"checkpoint":"/existing/checkpoint.md","message":"Initial user task"}` explicitly starts its first user turn after the receiver and observation are prepared; save its displayed worker ID. The JSON envelope keeps checkpoint paths separate from user text. Registration remains paused for supervisor delivery. If a prompt, input, session change or new turn interrupts setup, the provisional registration and initial message are discarded; inspect the interaction and repeat the command once idle. A provisional record is not restorable without its ready marker, even if cleanup fails. Pi's message API does not report acceptance: wait for an observed initial-run notice before binding a supervisor. If no matching run starts within 30 seconds, the worker is held; inspect the session and start a fresh session rather than blindly resending the uncertain message. Plain `/continuation-worker <existing-checkpoint-path>` registers observation-only; typing a separate task prompt after registration enters a sticky human-input hold.
2. In an existing coordinator if desired, `/continuation-coordinator`; save its displayed coordinator ID.
3. In the dedicated supervisor, `/continuation-supervisor init`, then `/continuation-supervisor add <worker-id> <workspace-id>`. The worker's Herdr native Pi session, terminal, pane, cwd and workspace must match; new routes start paused. `/continuation-supervisor coordinator <workspace-id> <coordinator-id>` binds an exact recipient.
4. Confirm any old continuation owner has **stopped** before activating a worker. Explicitly `/continuation-supervisor activate worker <id>`, `activate route <workspace-id>`, and `activate global`. One scope never lifts another. `/continuation-supervisor status` reports current scopes and pending disposition; `pause` has corresponding scoped forms. `/continuation-worker-clear-hold` is a human-confirmed worker hold clear, not a scope activation.

Coordinator sessions may be in another workspace; the route still identifies the workers' workspace. Registration rejects worker/control-role collisions and duplicate canonical checkpoint paths. That canonical path remains pinned during observation and disposition; a changed path isolates the worker. Repeating setup preserves existing pauses; a different coordinator cannot silently replace a binding. Explicitly reactivating a paused worker rearms unresolved attention once without replenishing its nudge budget or retrying an already delivered stop.

The supervisor model uses `continuation_disposition` to resume, acknowledge, pause, or issue one material notice per stop/kind. Resume and completion cite the pinned checkpoint; a blocker, decision or pause may cite the worker's pinned final reply. For completion, it must inspect the **whole assigned backlog**, cite an exact excerpt, and pass the full checkpoint's `reportHash` from its attention message. A standalone status marker is not required: narrative reports are interpreted by the model, while the extension checks the exact stop, cleared hold, cited evidence, unchanged report hash, and one-use disposition. A favorable review verdict alone is not proof that follow-up work is done. The hash rejects stale evidence; it does not prove the model's interpretation. Completion notices recheck the report at dispatch and at the recipient. An acknowledgement does not independently accept the assignment. Do not paste instructions disguised as model tool calls into the command line; activation is a TUI-confirmed human command only.

## Experimental SDK worker host (source preparation)

The package also declares `pi-continuation-worker`, an explicit SDK host requiring the verified **unmodified Pi 1.5.2 frontend profile**, exercised on Linux. It loads the continuation observer first through the public resource-loader API and preserves prompt observation for separate shortcut contexts and cached shared UI across reloads. The ordinary `pi -e` entry point does **not** acquire this coverage.

For a **separately authorized disposable** environment with the SDK peer available:

```sh
node src/worker.mjs --session /path/to/existing-saved-session.jsonl
```

`--continue` uses native recent-session selection (creating a session if none exists); omitting both flags starts a new native session. An explicit session must already be a non-empty file. Its saved working directory and model are retained; metadata-only branches also retain explicit thinking settings instead of taking SDK defaults. An unavailable saved model or SDK fallback is refused. Unsupported flags and positional messages are rejected, not sent to a model. Importing the module or asking for help does not start a host. Registration, all activation scopes and ownership transfer remain separate explicit actions.

Native settings/resource discovery, codemode, tool search and MCP factories are retained. The SDK helper requires the native process configuration directory (`PI_CODING_AGENT_DIR`, or Pi's default); filesystem aliases are accepted, but an unrelated custom root is refused before factories load. Project resources start untrusted; global `project_trust` handlers, native stored trust and explicit policy retain priority. Unknown projects need a human choice; only the explicit remember choice writes native trust. A replacement without a native trust UI or an existing decision stays untrusted rather than opening a concurrent console prompt. This is not Pi's configuration/package-management CLI. The native llama.cpp CLI extension has no public SDK factory here; `/llama` warns instead of becoming a model prompt, unless a configured extension supplies it.

Native interactive model login also holds the worker, including pending Core auth prompts that do not use extension UI. Core `/bug` and `/share` operations are observed through the public editor submission callback, preserving configured editors and native flows without focus/render interception. Their full-flow Promise is verified 1.5.2 runtime behavior, not the callback's void-typed API guarantee; other frontend versions and unsupported callback slots are refused. Finishing an operation does not clear its hold. Detected observer displacement blocks its host scope until restart; restoring an observer cannot rehabilitate earlier consent.

**Not accepted for existing workers.** The packed, symlinked executable was exercised through a real Linux PTY with temporary configuration and a synthetic paused registration, without a model request or real Herdr connection. This does not establish full native UI coverage, supervisor/worker judgment, Herdr runtime identity, selected-worker migration/recovery or macOS/Windows terminal behavior. No live installation or migration follows from these checks; activation remains default-off. See [validation](docs/validation.md#sdk-worker-host-source-preparation).

## Recovery and removal

Worker holds are persisted independently of working/settled outcomes. A completed stop with a missing, blank or over-8-KiB final reply is held for inspection, including retained older observations; reply evidence cannot justify resuming or declaring completion without checkpoint evidence. Older supervisor bindings without a pinned checkpoint restart worker-paused and need inspection and activation. Missing or older observations without a durable hold flag require inspection and explicit hold clearing; a new turn or restart cannot clear them. A confirmed pre-acceptance busy rejection leaves a notice pending for a later event; failures after acceptance remain uncertain and cannot be retried. Escape in a supervisor turn pauses the global scope.

State lives in a private per-user `~/.pi-continuation` directory; no state is written into this source tree. A lost Herdr subscription pauses the global scope. Crash or uncertain receipt **never** triggers blind retransmission. A new supervisor process cannot take an existing owner claim automatically: after confirming the previous process is gone, inspect its lock/socket and pending intents, then remove stale owner artifacts under the private state directory before explicitly initializing a new supervisor. Treat `sending` intents and `accepted` receipts as uncertain and pause the affected worker. Do not delete worker observations or reset budgets to make a retry work. The Unix socket pathname is removed on orderly shutdown; Windows uses named pipes. Never remove a live owner's lock or socket.

For an authorized disposable Pi installation, remove the package using `pi remove /absolute/path/to/pi-continuation` and stop the disposable sessions before cleaning state. This package never autonomously starts workers, migrates old supervisors, changes OS timers, installs Herdr integrations, or publishes npm. The optional first turn starts only when the user explicitly supplies the task message and confirms registration. Publication, live installation, real worker registration, migration and platform/runtime verification require separate explicit authority.
